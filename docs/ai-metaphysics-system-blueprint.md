# AI玄学系统蓝图

## 1. 项目目标

打造一个强大的 AI 玄学系统，最终形态参考 `https://app.cantian.ai/zh_cn/home`，但不局限于单一排盘工具，而是演进为具备多技能、多报告、多轮咨询、订阅变现能力的平台型产品。

项目起步阶段计划基于两个公开项目进行参考和复刻：

- `gaoxt/zhouwenwang`
- `cantian-ai` 体系下的公开仓库，重点是 `bazi-mcp`

核心策略不是简单复制任一项目，而是采用“直接基于开源代码改造”的路线：

- 以 `zhouwenwang` 作为首个可运行产品基座
- 以最小改动方式替换或增强八字命理能力
- 尽量复用现有页面、路由、状态管理和数据结构
- 只在必要处接入 `bazi-mcp` 或参天系能力

## 2. 总体选型判断

### 2.1 `zhouwenwang` 的价值

`zhouwenwang` 更接近成品产品形态，适合作为前期产品层参考来源。它更适合承担以下职责：

- 页面结构参考
- 用户交互流程参考
- 功能模块拆分参考
- Web 产品雏形和演示原型来源

适合作为前期快速搭建 MVP 的“产品壳”。

### 2.2 `bazi-mcp` 的价值

`bazi-mcp` 更适合作为命理算法能力层，承担以下职责：

- 八字排盘
- 历法转换
- 基础命盘结构化输出
- 作为独立服务向上游业务系统提供稳定输入

它不负责产品壳，也不应承担最终报告呈现和聊天编排职责。

### 2.3 `cantian-packages` 的价值

`cantian-packages` 更像基础设施层和公共库层，而不是可直接复刻的网站源码。它更适合：

- 研究参天的公共包拆分思路
- 借鉴基础能力模块化方式
- 参考后端公共组件和命理工具的包化设计

不建议把它作为第一起步项目。

## 3. 实施原则

当前阶段不建议从零开始重新搭建完整 monorepo、前后端和平台层。优先原则如下：

- `fork 优先`
- `能复用就不重写`
- `能外挂就不侵入`
- `先跑通再重构`
- `先保留单体结构，再逐步抽离服务`

也就是说，第一阶段目标不是做出“最优架构”，而是以最低成本做出一个可用、可演示、可持续迭代的版本。

## 4. 核心路线

项目分三层推进：

- 产品层：参考 `zhouwenwang`
- 算法能力层：接入 `bazi-mcp`
- 平台能力层：自行建设报告系统、AI 咨询编排、订阅体系、账号体系

原则上必须把以下三类能力彻底分层：

- 命理计算
- AI 解释与生成
- 前端展示与用户交互

这里的“接入”并不意味着立刻拆成独立系统。第一阶段建议：

- 产品壳、页面、交互、状态管理尽量沿用 `zhouwenwang`
- 先不重写整体前端结构
- 先不重做目录体系
- 只替换八字计算逻辑、数据接口和部分报告逻辑

## 5. 建议系统形态

建议把系统分成两个阶段来看：

### 5.1 第一阶段：基于 `zhouwenwang` 的单仓改造

当前最合理的做法不是新建多个 app，而是基于已有项目保留以下部分：

- 页面结构
- 路由结构
- 全局状态管理
- 已有交互组件
- 已有展示模块
- 基础后端代理层

在此基础上只做必要修改：

- 替换或增强八字排盘逻辑
- 替换 AI 解读生成策略
- 补用户数据持久化
- 补历史记录
- 补基础订阅能力

### 5.2 第二阶段：在跑通后再逐步拆分

当产品逻辑稳定后，再考虑把下面能力逐步抽离：

- 命理引擎服务
- AI 编排服务
- 报告异步任务服务
- 通用 UI 组件包
- 共享知识和模板包

## 6. 三阶段实施路线

## 6.1 第一阶段：MVP

目标是在 2 到 3 周内做出一个真正可演示的闭环。

本阶段只做一个核心术数：`八字`。

首批功能：

- 首页
- 八字排盘
- 基础命盘展示
- AI 简版解读
- 历史记录
- 用户登录

MVP 数据流：

1. 用户输入出生信息
2. 现有项目中的排盘入口调用增强后的八字能力
3. 系统存储 `chart`
4. AI 解读模块基于命盘和模板生成基础解读
5. 前端展示并允许用户继续追问

本阶段刻意不做：

- 六爻
- 奇门
- 手相
- 解梦
- 复杂专家市场
- 过多营销页面

## 6.2 第二阶段：可商用版

目标是在 1 到 2 个月内补齐可售卖和可持续运维的核心能力。

重点功能：

- 年度运势报告
- 大运流年分析
- 多轮 AI 咨询
- 订阅与额度体系
- 报告缓存与版本管理
- 管理后台
- 埋点与效果评估

该阶段重点不在于单纯放大模型，而在于稳定输出：

- 固定报告模板
- 分段生成
- 结论与依据分离
- 敏感内容约束
- 生成结果可回溯

## 6.3 第三阶段：参天式平台化

目标是从单一排盘工具升级为技能平台。

候选 skill：

- 八字 skill
- 合婚 skill
- 流年择日 skill
- 六爻 skill
- 奇门 skill
- 起名 skill
- 事业专题 skill
- 情感专题 skill
- 财富专题 skill

每个 skill 统一抽象为：

- 输入协议
- 计算器
- 知识上下文
- 输出模板
- 对话策略
- 付费策略

## 7. 第一阶段的最小改动范围

建议只动以下几类地方：

### 7.1 必改

- 八字排盘实现
- 排盘结果数据结构
- AI 解读提示词和输出模板
- 历史记录持久化
- 登录和用户关联

### 7.2 可后置

- 全站视觉重做
- 完整订阅系统
- 多术数统一技能中心
- 独立 worker
- 完整微服务化

### 7.3 尽量不动

- 大部分现有页面结构
- 大部分组件拆分方式
- 全局状态流转方式
- 能复用的表单和展示层代码

## 8. 核心领域对象

建议优先设计以下五个核心对象：

- `user`
- `chart`
- `report`
- `conversation`
- `skill`

建议最小数据模型方向：

### 6.1 `chart`

- 出生信息
- 时区
- 排盘结果 JSON
- 算法版本
- 来源版本

### 6.2 `report`

- 报告类型
- 输入快照
- 输出内容
- 模型版本
- 状态

### 6.3 `conversation`

- 关联 `chart`
- 关联 `skill`
- 消息上下文
- 剩余额度或权限

### 6.4 `skill`

- 名称
- 参数 schema
- 模板
- 知识源
- 生成策略

### 6.5 `subscription`

- 套餐
- 剩余额度
- 有效期
- 权益范围

## 9. 技术建议

推荐技术方向如下：

- 第一阶段前端：优先沿用 `zhouwenwang` 现有技术栈
- 第一阶段后端：优先沿用现有代理和接口方式
- 数据持久化：按现有代码结构选择最容易接入的方案
- 模型接入：统一收敛到一层服务或一组稳定接口
- 命理接入：优先以适配层方式接入 `bazi-mcp`

核心技术原则：

- 不大规模推翻现有代码结构
- 不在第一阶段建立过重基础设施
- 排盘逻辑和 AI 解读逻辑要能分开替换
- 排盘结果必须带版本号
- 报告生成必须可缓存、可追溯

## 10. 使用开源项目的方式

建议的组合方式：

### 8.1 `zhouwenwang`

用途：

- 参考产品结构
- 参考页面布局
- 参考交互流程
- 参考功能模块拆分
- 作为第一阶段直接改造基座

### 10.2 `bazi-mcp`

用途：

- 作为八字计算增强内核
- 先通过适配层接入
- 提供更稳定的命盘 JSON

### 10.3 `cantian-packages`

用途：

- 研究基础库拆分方式
- 参考包化设计
- 后续借鉴其后端模块组织方式

## 11. 主要风险

### 9.1 业务和产品风险

- 一开始术数铺得太多
- 报告与咨询链路没有先做稳定
- 没有订阅和额度体系，后续难以商业化

### 11.2 架构风险

- 前端直接拼 prompt 出报告
- 命理规则和 AI 话术混在一起
- 排盘结果没有版本控制
- 报告生成不做缓存，成本不可控
- 一开始为了“最优架构”而过度重构开源项目

### 11.3 合规与授权风险

- `zhouwenwang` 若未明确许可证，不宜直接商用
- 需要尽早核查依赖、素材、提示词和生成内容的合规边界

## 12. 当前建议结论

一句话执行建议：

直接基于 `zhouwenwang` 改，优先保留其现有结构，只在 `八字排盘 + AI解读 + 历史记录 + 登录` 这条主链上做最小改动，并用 `bazi-mcp` 逐步替换命理核心能力。
