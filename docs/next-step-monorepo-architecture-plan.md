# 下一步方案设计：基于开源代码的最小改动实施计划

## 1. 调整后的总原则

当前路线从“从零设计新系统”调整为“直接基于开源项目改造”。

优先级如下：

1. 先直接跑通开源项目
2. 在原结构上做最小改动
3. 先替换核心能力，再谈架构升级
4. 先做八字主链，其他术数延后

这意味着当前阶段不应该先做：

- 从零建 monorepo
- 从零重写前端
- 从零重写后端
- 先拆微服务

## 2. 基座选择

第一阶段明确以 `zhouwenwang` 作为改造基座。

原因：

- 它更接近成品产品
- 有现成页面、路由、交互和状态流
- 更适合快速做出可运行 MVP
- 相比参天公开仓库，它更像“产品壳”

`bazi-mcp` 的角色不是基座，而是能力增强模块。

## 3. 第一阶段只做的事

只围绕一条主链改造：

- 八字排盘
- AI 解读
- 历史记录
- 登录关联

如果基座里已经有相近功能，则优先复用并替换内部实现，而不是重做页面。

## 4. 第一阶段尽量不做的事

- 不改全站技术栈
- 不改整体目录结构
- 不重做 UI 风格
- 不一开始加六爻、奇门、手相、解梦
- 不先建复杂订阅平台
- 不先追求参天式 skill 平台

## 5. 改造策略

建议采用“保留外壳，替换内核”的方式。

### 5.1 保留部分

优先保留：

- 页面布局
- 路由结构
- 导航结构
- 现有展示组件
- 现有表单交互
- 状态管理方式
- 能直接跑通的后端代理结构

### 5.2 替换部分

优先替换：

- 八字排盘核心逻辑
- 排盘结果 schema
- AI 解读 prompt 和输出格式
- 历史记录的数据持久化方式
- 用户登录后的数据绑定方式

### 5.3 延后部分

后面再做：

- 深度报告异步化
- 多 skill 抽象
- 订阅额度系统
- 后台管理
- 微服务拆分

## 6. 建议的代码改造顺序

不先设计理想架构，先按代码侵入面最小的顺序推进。

### 6.1 第一步：拉起 `zhouwenwang`

先做：

- 跑通本地开发环境
- 确认前端入口
- 确认后端入口
- 确认八字相关页面、状态、接口和提示词位置

目标不是改代码，而是找到最小改造路径。

### 6.2 第二步：定位八字主链

重点要找清楚：

- 八字输入表单在哪
- 表单提交到哪里
- 排盘逻辑是在前端、后端还是 prompt 中
- AI 解读在哪里拼接
- 历史记录是本地存储还是服务端存储

只有找到这条主链，后续改动才会小。

### 6.3 第三步：接入 `bazi-mcp`

接入方式建议按侵入性从低到高排序：

1. 先用适配函数包装 `bazi-mcp`
2. 用适配函数输出和现有页面兼容的字段
3. 只替换八字页面依赖的数据源
4. 页面展示层尽量不动

不要一上来就把所有数据结构都改掉。

### 6.4 第四步：替换 AI 解读层

建议保留原有用户交互形式，只替换：

- 系统提示词
- 输入上下文组织方式
- 输出结构

最稳的做法是让 AI 不再直接“猜命盘”，而是只解释结构化命盘结果。

### 6.5 第五步：补持久化

如果原项目历史记录依赖本地存储或临时状态，则最先补：

- 用户表
- chart 记录表
- 报告表

这一步只做最小持久化，不先做复杂运营后台。

## 7. 实际应检查的代码区域

等代码拉下来后，优先检查以下内容：

### 7.1 前端

- 八字页面组件
- 创建排盘表单
- 命盘结果展示组件
- AI 对话或报告组件
- 历史记录页面

### 7.2 状态层

- 八字输入状态
- 当前结果状态
- 历史记录状态
- 用户状态

### 7.3 服务层

- API 请求封装
- 后端代理接口
- 第三方模型调用位置
- Prompt 模板位置

### 7.4 数据结构

- chart 对象
- message 对象
- history 对象
- 报告对象

## 8. 第一阶段推荐的最小数据模型

即使沿用开源项目，也建议尽快固定最小数据结构。

### 8.1 `chart`

- `id`
- `userId`
- `input`
- `result`
- `engineVersion`
- `createdAt`

### 8.2 `report`

- `id`
- `chartId`
- `type`
- `content`
- `modelVersion`
- `createdAt`

### 8.3 `user`

- `id`
- `email` 或匿名标识
- `createdAt`

这一步的目标是让系统“有记忆”，而不是先做完美表设计。

## 9. 第一阶段推荐的最小接口

如果原项目已经有接口，就尽量复用命名和调用方式。只要满足下面三件事即可：

- 创建 chart
- 获取 chart
- 生成基础解读

最小接口能力：

- `createChart`
- `getChartById`
- `createBasicReport`

如果原项目是前端直连模型，则建议新增一层最薄的服务端代理，不要继续让浏览器直接承担核心逻辑。

## 10. 第一阶段的成功标准

只要满足下面几点，就算第一阶段方向正确：

- 能直接运行 `zhouwenwang`
- 能找到八字主链代码
- 能把八字结果替换为更稳定的命盘输出
- 页面层改动不大
- AI 解读不再完全依赖自由生成
- 用户可查看自己的历史排盘

## 11. 当前最合理的下一步

下一步不该继续写抽象方案，而应该直接进入代码层面：

1. 把 `zhouwenwang` 拉到本地
2. 跑起来
3. 识别八字主链相关文件
4. 给出“最小改动清单”
5. 再开始动代码

## 12. 需要提醒的风险

- 如果 `zhouwenwang` 没有明确许可证，商用前要先确认授权
- 如果其八字实现和页面强耦合，直接替换时可能需要做一层字段适配
- 如果原项目大量依赖 Gemini 直出，报告稳定性会是第一批问题

## 13. 当前结论

下一步不应该从零搭骨架，而应该围绕 `zhouwenwang` 做一次代码级接管：

- 保留产品壳
- 定位八字主链
- 用 `bazi-mcp` 或兼容适配层替换排盘核心
- 只补最必要的数据持久化和用户关联

这才是“最小改动、最快落地”的正确路线。
